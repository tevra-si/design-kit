# Expanded v2 commands

Build once with `pnpm install` and `pnpm build`; invoke the repository binary as `pnpm tevra-design` (or `node dist/packages/cli/src/index.js`). Every command accepts `--root /absolute/project`. Input/output paths are relative to that project.

```sh
tevra-design skills list
tevra-design skills inspect frontend-review
tevra-design skills validate
tevra-design skills graph
tevra-design skills list --registry extensions/acme.json
tevra-design context show
tevra-design context validate
tevra-design context migrate old-context.json --out .tevra/migrated.json
tevra-design memory list
tevra-design memory reset --yes
tevra-design workflow plan "Build a dashboard" --mode full --max-steps 12
tevra-design workflow run .tevra/plans/PLAN-ID.json
tevra-design workflow status .tevra/plans/PLAN-ID.json
```

Graph returns JSON containing Mermaid. Registry extension files use the same schema as the bundled registry and may depend on core skills. They are metadata, not agent executables. A full new-interface plan currently selects ten relevant skills; it does not invoke motion/redesign without intent.

## Executing instructional stages

The coding agent reads the selected SKILL.md and carries out its instructions. It records verified artifacts with:

```sh
tevra-design workflow start .tevra/plans/PLAN-ID.json --skill design-research
tevra-design workflow complete .tevra/plans/PLAN-ID.json --skill design-research --evidence design-research.md
```

After required instructional stages pass, `workflow run` can execute supported local QA adapters. Missing integration/browser/app resources produce blocked status and an evidence record. No blocked or skipped check is reported passed. Unapproved high-impact workflows require `workflow approve ... --by NAME --yes` after review of their plan; CLI approval records the supplied human decision and does not generate consent.

## Browser and visual checks

```sh
tevra-design doctor --launch
tevra-design capture --kind baseline --approve-baseline
tevra-design test browser
tevra-design test accessibility
tevra-design test visual
tevra-design report
```

Accepted baseline manifests are never overwritten. Archive an accepted baseline explicitly before establishing a replacement. `test visual` captures current state, compares against an existing baseline and generates a quality report. `test browser` requires explicit assertions in every configured state; action success alone is insufficient. Console errors and network failures are separate findings. Manual keyboard/screen-reader/visual judgment remains necessary beyond automated checks.

`report` writes `.tevra/reports/quality.json`, `quality.md` and `quality.html`. `--checks extra-checks.json` supplies separately labeled observations with existing local evidence. Never submit fabricated score/evidence to make a gate green.

## Laboratory performance

```sh
tevra-design test performance --allow-network --lcp-ms 2500 --cls 0.1 --tbt-ms 200
```

Requires installed Lighthouse, Chromium and a reachable app. The explicit network flag permits the target's resource requests during Lighthouse auditing; review those origins first. Custom browser executables additionally require `--allow-custom-browser`. The command writes a unique run's Lighthouse JSON/HTML and metric summary under `.tevra/artifacts/performance/`; failed attempts are recorded. It does not query CrUX, infer real-user INP or automatically approve regressions.

Exit codes: 0 executed command/gate passed, 1 failed or blocked workflow/quality outcome, 2 invalid input or environment error. Inspect the JSON status and limits as well as the exit code.
